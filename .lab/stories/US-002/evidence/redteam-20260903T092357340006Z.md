# Red Team Report

## Confirmed defects

- **Observation:** Calling `GameController.open_profile()` a second time after a profile is active raises the domain-level `InvalidTransitionError` directly. Unlike `begin_recovery()` and `submit_recovery()`, `open_profile()` does not translate this transition failure into `GameControllerError`. The UI’s profile handler catches only `GameControllerError`.
- **Inference:** Repeated or overlapping profile-open events, such as a rapid double click, can escape the UI-safe error boundary and interrupt the interaction.
- **Recommendation:** Catch `InvalidTransitionError` inside `open_profile()` and raise `GameControllerError`; add a test covering repeated and concurrent profile-open attempts.

## Suspected defects

- **Observation:** The runtime evidence establishes server startup and HTTP 200, but visual browser automation and click-through testing are explicitly untested.
- **Uncertainty:** It has not been demonstrated that the player can complete browse → profile → chat → bank → result through rendered controls in the pinned Flet runtime.
- **Recommendation:** Complete and record successful and failed rounds using a real browser or Flet client.

- **Observation:** `Settings.max_messages` accepts any integer, while `GameController` rejects values below one during application startup.
- **Inference:** `CATFISH_MAX_MESSAGES=0` or a negative value terminates startup instead of producing a typed configuration error or usable fallback.
- **Uncertainty:** Invalid configuration behavior is not part of US-002’s explicit acceptance criteria.
- **Recommendation:** Add `Field(ge=1)` to the setting and test invalid environment configuration.

## Missing tests

- A pinned-runtime browser test covering the complete successful round.
- The same browser flow with an incorrect answer and visible `RECOVERY FAILED`.
- A controller test proving every illegal public operation produces `GameControllerError`, including repeated `open_profile()` and invalid `next_round()`.
- A concurrency test for repeated profile-open events.
- A UI-boundary inspection proving rendered profile controls and serialized public profile values contain no private record or recovery-answer fields.
- A browser assertion that the seeded portrait loads successfully, rather than only checking filesystem existence.
- A clean-process startup test with invalid `CATFISH_MAX_MESSAGES` values.

## Design concerns

- **Observation:** Controller transition errors are translated individually in several methods rather than through one consistent controller boundary.
- **Inference:** New or overlooked operations can leak domain exceptions to UI code, as `open_profile()` currently does.
- **Recommendation:** Centralize transition-error translation or require a test asserting the exception contract of every controller operation.

- **Observation:** Route state, closure-local `runtime` state, and controller state remain separate.
- **Inference:** Correct rendering still depends on synchronization among three state stores, despite guards for known inconsistent routes.
- **Recommendation:** Make controller phase and active profile authoritative and derive route presentation state from them where practical.

## Areas tested without finding a defect

- **Observation:** Both accepted recovery answers produce success, while each supplied incorrect-answer combination prevents success.
- **Observation:** Normalization is deterministic and tested for idempotence.
- **Observation:** Public and private persona models are distinct, and extra recovery data is rejected by `PublicProfile`.
- **Observation:** The controller verifies that the private record matches the selected public profile.
- **Observation:** Chat provider failures and private-record provider failures are translated to UI-safe controller errors.
- **Observation:** Invalid chat route identity is rejected.
- **Observation:** Browse fallback actions abandon the current round and restore browsing state.
- **Observation:** The result explicitly distinguishes successful and failed recovery and presents a defensive lesson.
- **Observation:** The seeded portrait path is covered by an existence test and supplied evidence reports its SHA-256 check passing.
- **Observation:** Supplied evidence reports Ruff, Lab doctor, pytest, and API-key-free pinned-runtime startup passing.
