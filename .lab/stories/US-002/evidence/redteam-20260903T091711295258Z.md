# Red Team Report

## Confirmed defects

- **Observation:** From a `CHATTING`, `RECOVERY`, or `RESULT` state, navigating directly to a guarded route such as `/bank` or `/result` can display a “Browse” button. That button only navigates to `/browse`; it does not reset the controller. Opening a profile there then fails because `RoundState.open_profile()` only permits opening while `BROWSING`.
- **Inference:** The UI can place the player on a browse surface that cannot start a round, requiring an application restart or restoration of the previous route.
- **Recommendation:** Route fallback actions should either return to the valid route for the current phase or explicitly abandon/reset the round through a controller operation.

## Suspected defects

- **Observation:** `observed_behaviors` reports “shared personal history in casual conversation” whenever any chat message exists, without inspecting the canned reply or whether a recovery fact was disclosed.
- **Inference:** A player who sends one unrelated message may receive a misleading debrief.
- **Uncertainty:** The acceptance criteria require a defensive debrief but do not define the accuracy standard for behavior descriptions.
- **Recommendation:** Derive behavior evidence from explicit provider metadata or use neutral copy such as “conversation occurred.”

- **Observation:** The supplied evidence contains no execution results for the pinned Flet version.
- **Uncertainty:** Component state, async handlers, routing, and `page.render()` compatibility remain unverified.

## Missing tests

- An end-to-end UI test covering browse → profile → chat → bank → successful result.
- The same end-to-end flow with an incorrect answer and visible `RECOVERY FAILED`.
- A route-recovery test proving fallback buttons leave the controller and displayed route in a usable state.
- A controller test with a provider returning a private record whose `profile_id` differs from the selected public profile.
- A test proving the chat provider receives the same private record throughout the round.
- A boundary test inspecting all UI-facing values, rather than only asserting that `PublicProfile` lacks a `recovery` attribute.
- A test that canned replies remain deterministic across fresh provider/controller instances.
- A clean-environment launch test demonstrating operation without an API key.

## Design concerns

- **Observation:** Route state and controller state are maintained separately, while fallback navigation mutates only route state.
- **Inference:** Additional route/state inconsistencies are likely unless navigation is centralized around valid controller transitions.
- **Recommendation:** Map every controller phase to an authoritative route and redirect invalid routes accordingly.

- **Observation:** The portrait path `faces/demo-sam.webp` is referenced, but no corresponding asset was supplied in the visible context.
- **Uncertainty:** The profile may render without its intended portrait, or the current UI may simply never display the asset.

## Areas tested without finding a defect

- **Observation:** Recovery comparison is deterministic and requires both accepted answers.
- **Observation:** Normalization handles Unicode normalization, case, punctuation, and whitespace deterministically.
- **Observation:** The seeded provider requires no live AI or profile-generation API.
- **Observation:** Public and private persona models are distinct, and extra recovery data is rejected by `PublicProfile`.
- **Observation:** The controller validates that the private record belongs to the opened public profile.
- **Observation:** The explicit state machine prevents recovery without an active target and rejects target changes during submission.
- **Observation:** The result label explicitly distinguishes successful and failed recovery.
- **Observation:** Recovery telemetry records match outcomes without logging raw submitted or canonical answers.
